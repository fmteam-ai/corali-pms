# Hotel Corali PMS v92 — release verification

## Scope in this package

### New in v112 — room temperature / humidity sensors with alerts
- Rooms → Air conditioning: "Temperature / humidity (Tuya ID)" per room (Tuya Wi-Fi thermo-hygrometers through the Tuya connection). Read every ~10 minutes by the message automations cron ("Read now" in the PMS); shows °C, %, battery and time.
- Alerts (thresholds on the same page): damp room (humidity ≥ 70 % for 3 hours, once a day); room with a guest that stays outside 17–28 °C while the A/C has had power for 60 minutes (PMS notification + maintenance notice, at most twice a day); sensor battery ≤ 20 % (once a week).
- The TV assistant knows the room's current temperature / humidity (readings under an hour old).
- Database: room_climate; tv_power_settings gains climate thresholds.

### New in v111 — TV assistant suggests beaches by the wind (meltemi)
- The assistant reads the wind for Piso Livadi (Open-Meteo: direction, Beaufort, gusts, 3-day forecast; wave height from the marine API when available) and, from ~4–5 Bf / with the meltemi, suggests the nearest beaches sheltered from that wind and says why; exposed beaches are mentioned as windy (windsurf / kite).
- PMS → Corali TV → "Beaches for the assistant": name, minutes from the hotel, which winds it is sheltered from (Βοριάς … Μαΐστρος), note. Starts with a suggested Paros list — check it with local knowledge.
- Ready question "Which beach today, with this wind?" in the six languages.

### New in v110 — TV assistant without QR, TV screens follow PMS updates
- Assistant tab: the "booking and services" QR code is removed (it stays on the home screen); the conversation uses the full width.
- TV screens check /api/health every 5 minutes and reload when the version changes, so a new installation reaches the room TVs without restarting them (screens still on v109 or older pick it up at their next 6-hour reload or a restart).

### New in v109 — AI assistant on the room TV, with voice
- PMS → Corali TV → "AI assistant on the TV (with voice)" (off by default) and questions per room per day (default 40). Needs the Anthropic key (Connections).
- TV "Assistant" tab during a stay: press 🎤 and speak into the remote's microphone (Corali TV app 1.5: the TV's own voice input; remotes whose microphone/search key reaches the app open the assistant directly), ready questions, or type. Answers in the guest's language, short, read aloud (🔊 on/off), from the hotel's facts, TV information, departments/services, offers and the area (web search).
- It can propose one request to reception (towels, cleaning, pillows, blankets, toiletries, call me) or an order / appointment from the departments (charged to the room as in the guest portal); it runs only when the guest presses Confirm. A new question cancels an unanswered proposal.
- The conversation belongs to the stay and is removed when the next stay uses the room.
- New APK: public/downloads/corali-tv.apk 1.5 (versionCode 6), same signing key — install over the old app with Downloader (booking.hotelcorali.gr/tvapp). Older apps show the tab without the microphone.
- Database: tv_assistant_messages, tv_assistant_actions.

### New in v108 — room A/C control (Shelly relay + Tuya presence sensor)
- Rooms → Air conditioning: each room's A/C on a Shelly relay (e.g. Shelly 1PM Gen4, Device ID per room). Power only while a guest is checked in; cut at check-out (at once, and every 5 minutes by the TV power cron). Staff can switch any room on / off: manual ON in an empty room lasts 3 hours, manual OFF in an occupied room until check-out or "Back to automatic".
- Optional presence sensor (Tuya mmWave, Wi-Fi): PMS → Connections → Tuya (Access ID / Secret, data center). With "presence sensor" on, the A/C is cut when nobody was in the room for N minutes (default 20) and powered again within ~1 minute when the guest returns (read every minute by the message automations cron). No sensor reading → the A/C keeps power.
- Uses the Shelly Cloud account of Corali TV → TV power. TV plugs (e.g. Shelly Plug M Gen3) work as before.
- Database: new table room_ac_devices, provider_tokens; tv_power_settings gains acEnabled / acPresence / acAwayMinutes.

### New in v107 — Channex rates & webhook, open API, automatic pricing, app store
- Channex: PMS → Integrations → Channel Manager → "pushRates = yes" sends the PMS nightly price per room type with the restrictions (optional OTA markup %). "Webhook Channex" creates a secret link; add it in Channex → Settings → Webhooks (event booking) and OTA bookings arrive in seconds.
- Open API (PMS → API & Webhooks): API keys with scopes (rooms, availability, bookings, folio charges for POS, accounting), `/api/v1/*` on the PMS address only, 120 requests/minute/key; POS charges by booking reference or room number with `external_id` against double charging. Webhooks (booking created/updated/cancelled/check-in/check-out, folio charge/payment) signed with `Corali-Signature` HMAC-SHA256, retried up to 10 times, sent by the automation cron.
- Automatic pricing (Prices → Automatic pricing): per room type minimum / maximum, demand bands, last minute, early booking, weekend, competitors' median, maximum change from base. "Suggestions only" shows the nightly prices; "Apply automatically" writes one-night prices (hidden from the season list) used by the booking engine and Channex. Runs hourly in the automation cron.
- App store (Global → App store): every integration and module with its state and setup page; partners (POS, accounting, Zapier/Make) connect through the open API.
- Database: run the schema update (the installer does it) — new tables api_keys, api_webhooks, api_webhook_deliveries, api_booking_state, api_event_cursor, auto_pricing_settings, auto_price_days; new columns channel_sync_state.webhook_*, rate_rules.source.

### New in v104 — PMS assistant that acts, with approval

- The dashboard AI assistant can now **propose actions** with a `propose_actions` tool: message a guest (booking conversation + e-mail), message on room TVs, news / offer / happy hour in guests' My booking, report a defect, add a folio charge, set a period price, issue a digital key.
- Nothing runs on its own: each proposal is stored as **pending** (`assistant_actions`) and shown as a card under the answer with **Approve / Reject**. Approving runs it with the existing PMS functions and needs the action's own permission (folio charge → `folios.write`, period price → `pricing.create`, defect → `housekeeping.write`, the rest → `reservations.write`); staff without it see "needs approval by a colleague". A proposal runs once (atomic claim); every decision is in the audit log.
- Bookings and room codes are checked when proposed; unknown ones are refused back to the assistant, which tells the staff member.
- Works without web search too (proposals still offered when the web-search tool is unavailable).
- Verified in dev with a mocked Claude: 3 proposals stored, an unknown room refused, approving ran the guest message, the defect (with its notification) and the €12.50 folio charge; audit rows written.

### New in v102 — digital keys (virtual access card)

- PMS → Bookings → **Digital keys** (`/pms/access-cards`), switched on/off from the page (off: no cards are issued and every door check answers no).
- Every confirmed booking gets a card automatically the day before arrival (from the sending time, default 10:00; later or same-day bookings at once), by the existing message-automation cron, and an e-mail in the guest's language with the card link (`/card/<token>`, booking domain). The card shows the hotel logo, the guest's name, room, validity, areas and a QR code, with **Add to Apple Wallet** (signed .pkpass) and **Add to Google Wallet** (signed save link).
- Valid from check-in time on the arrival day until **11:00 on the departure day** (both configurable). Booking cards follow the booking: new dates, room moves, and a cancelled / no-show / checked-out booking ends the card at once.
- Reception can extend (new end, which then stays as set until "Follow the booking again"), change areas, resend, show the link + QR, or cancel a card; the change is pushed to cards already saved in Google Wallet.
- Manual cards for walk-ins / visitors: name, optional e-mail, room and/or areas, start and end; the link + QR are shown to scan on the spot.
- Hotel areas (gym by default) are configurable; "Guests" marks the areas every booking card gets.
- Wallet set-up in Settings. Apple: the PMS creates the RSA key (it never leaves the server) and the certificate signing request; the hotel uploads the CSR to Apple for its Pass Type ID certificate and uploads the .cer back (a certificate for another key is refused), plus WWDR G4 and an optional NFC key (Apple's NFC entitlement). Google: issuer ID, service-account key, optional Smart Tap. Secrets are stored encrypted; the certificate subject and expiry are shown.
- Pass signing uses Node's own crypto (`lib/cms.ts`: CSR and detached CMS SignedData) — no third-party crypto library (node-forge was tried and dropped: every published version had open advisories or was too new for the release-age policy).
- Door readers / lock controller: `POST /api/public/access/verify` with `Authorization: Bearer <reader key>` and `{credential, zone: "room"|area, room}` → `{allow, reason}`; every answer is logged under **Access log**. The reader key is shown once.
- Verified in dev: card issued by the cron for tomorrow's arrival (14:00 → 11:00, gym only), .pkpass signature (certificate issued by a test CA from the PMS CSR) verifies with OpenSSL, a tampered manifest fails, the manifest hashes match, a .cer for another key is refused, Google JWT verifies with the service-account key, door checks: OK / ZONE_NOT_ALLOWED / WRONG_ROOM / NOT_YET_VALID / REVOKED after booking cancellation / 401 with a wrong key.

### New in v88 — Channex review (against the channex-pms-integration guidance)
- OTA modifications are applied in place (scripts/channel-core.mjs planRevision): dates, price, guests updated on the same PMS booking; the room is kept when still free (else reassigned); added rooms inserted, dropped rooms cancelled, checked-in stays never cancelled. Before, a modification cancelled and re-created the booking (lost room/folio links and could hit the unique external-booking index, leaving the revision unacknowledged until it expired from the feed).
- Never sell a room twice: OTA bookings imported without a free room keep their room type (bookings.external_room_type) and still reduce the availability sent to Channex (AVAILABILITY_SQL, shared by the job and the PMS check).
- Feed drained page by page (10 per page) instead of one page per run; a failing revision does not block the others and raises a PMS alert at once (unacknowledged revisions drop out of the Channex feed after ~30 min). Cancellations set cancelled_at.
- Run order: import first, then push availability in the same run. Hourly full 500-day push as drift correction. Runs never overlap (advisory lock), so the cron can run every minute (docs updated: `* * * * *`). Last run / error stored in channel_sync_state.
- PMS → Integrations → "Έλεγχος σύνδεσης Channex" (read-only): key/property reachable, every room type mapped to a Channex room type of the property, Channex room counts vs PMS, availability read-back for 14 days vs what the PMS would send, OTA revisions waiting, last successful run. ## Behaviour changes to note before installing

- Reception no longer edits rates, catalogue or connections and no longer sees reports; Read-only no longer sees financial data or connections (specification defaults). Grant exceptions per user in Users & permissions.
- The website shows the standard rate struck through and charges the direct rate (−5% by default). Adjust or switch off in PMS → Rates.
- The shared BIRTHDAY10 code is retired in favour of personal codes.
- Housekeeping and Reception gain the new `maintenance.resolve` permission (resolve defects); Read-only does not.
- Existing message-automation settings keep working; the three new messages are switched on by default but only send once automations are saved again with templates (defaults are pre-filled).
- Fixed: the review message was scheduled far in the future because BIGINT settings were read as text.
